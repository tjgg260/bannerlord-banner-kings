# Bannerlord Open World

A Mount & Blade II: Bannerlord mod project to make the world walkable in 3D: large regional scenes the player walks across on foot, with terrain, settlements and parties streamed in and out around them instead of the abstract campaign map plus separate battle/town scenes.

Started as an experiment inside the Banner Kings fork (`tjgg260/bannerlord-banner-kings`, branch `terrain-streaming-prototype`). That branch holds the first prototype code.

## How Bannerlord is built (what we can and can't change)

- **Managed C# layer**: `TaleWorlds.*.dll` (CampaignSystem, MountAndBlade, Core, Engine, ...). Decompiles cleanly with dotPeek/ILSpy/dnSpy. Game logic, campaign AI, missions, agent spawning and scene transitions live here. We change it with our own C# plus Harmony patches.
- **Native C++ engine**: `TaleWorlds.Native.dll`. Rendering, terrain, physics, navmesh, scene loading, animation. No source and no symbols. It can only be disassembled (Ghidra/IDA), not decompiled into editable source. Changing it means runtime hooks (a C++ DLL using e.g. MinHook, loaded by the mod), which can break on every game update.
- C# can only call native functions the engine exports to it. Those declarations live in `TaleWorlds.Engine.dll`, `TaleWorlds.DotNet.dll` and `TaleWorlds.DotNet.AutoGenerated.dll` (the `ScriptingInterface*` / `EngineMethod` declarations). **If a capability isn't in that list, C# can't do it.**
- Legal: never commit or redistribute TaleWorlds DLLs or decompiled TaleWorlds code. Keep them local or in a private location. Check the EULA before publishing anything built on native reverse engineering.

## Known limits

- Vanilla battle size slider caps at 1000. A community-reported engine limit is ~2048 agents (a mounted unit counts as 2). Mods like BattleSizeResized go higher, and a video reportedly showed ~15,000 agents in one battle (source and method still to confirm). So the agent cap is patchable somehow.
- Mission scenes are bounded maps loaded all at once. There's no built-in world streaming.
- Navmesh is baked per scene. Agents can't walk where there is no navmesh.

## Approach

Build streaming ourselves on top of what C# can already do:

1. **One large scene per region** (a province), with its spawn points, roads and base navmesh.
2. **Terrain as mesh tiles**: cut the region into tiles (e.g. 500 m x 500 m). Each tile is a prefab with a static mesh, a collision body and its own navmesh prefab. C# spawns tiles near the player (`GameEntity.Instantiate`) and removes them behind (`GameEntity.Remove`).
3. **Content streaming**: villages, camps, props and agents spawned and removed around the player the same way.
4. **Campaign simulation keeps running underneath**. Campaign parties become real agents only when near the player.
5. **Region-to-region transitions** use a short loading screen (MMO-style zones).

Seamless terrain with no loading screens at all would need the native engine to load and unload terrain tiles. That's unknown, and probably needs native hooking.

## Prototype status (branch `terrain-streaming-prototype`)

Not yet compiled or run.

- `BannerKings/Behaviours/Streaming/StreamingRegion.cs` defines a region: a tile grid, tile prefab naming pattern (`bk_tile_{x}_{y}`), tile size, origin, and load/unload radii (600 m / 900 m, so walking along a border doesn't thrash). Includes a test region: a 4x4 grid of 500 m tiles in scene `bk_stream_test`.
- `BannerKings/Behaviours/Streaming/TerrainStreamingBehavior.cs` is a `MissionLogic`. Each tick it loads tiles near `Agent.Main` and unloads far ones. The initial load is all at once; after that it loads at most 1 tile per tick, closest first. It shows an on-screen message for each load and unload with the time taken in ms. It imports a per-tile navmesh once (never removed; no removal call is known).
- `BannerKings/Main.cs` adds the behavior in `OnMissionBehaviorInitialize` only when the mission's scene is a registered streaming region.

Unverified APIs (check in dotPeek first):
- `Scene.ImportNavigationMeshPrefab(string, int)`: does it exist, and what does the int (group shift) actually do?
- Is there any call to remove imported navmesh faces?

## Next steps

1. **Map the exported engine API.** Decompile `TaleWorlds.Engine.dll`, `TaleWorlds.DotNet.dll`, `TaleWorlds.DotNet.AutoGenerated.dll` and `TaleWorlds.MountAndBlade.dll`. List every native function exposed to C#, and look especially for terrain, navmesh, scene-loading and agent-limit functions. Unused exports may give us capabilities with no native patching.
2. **Compile the prototype** and fix any API mismatches against the installed game version.
3. **Build the test content** in the Modding Kit: a base scene `bk_stream_test` with a spawn near (1000, 1000), tile prefabs `bk_tile_0_0` .. `bk_tile_3_3` (each 500 m, corner at its origin, with collision), and navmesh prefabs `bk_tile_navmesh_X_Y`.
4. **Add a console command** that opens a mission in `bk_stream_test` with the player spawned (Bannerlord has no simple built-in way into a custom scene).
5. **Run the two key tests:**
   - Are load and unload hitches acceptable? (watch the ms messages)
   - Can agents walk across tile borders? (navmesh joins)
6. **Agent cap**: find out how the 15k-agent battle was done (config, C# patch or native patch). If it needs native patching, use it as the first, simpler native-hook project before attempting terrain.
7. Only then consider native hooks (Ghidra on `TaleWorlds.Native.dll`, MinHook-based DLL loaded by the mod) for anything C# can't reach.
